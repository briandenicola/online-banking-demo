**Question:** AKS moved Foundry agent provisioning to an initContainer (`python -m app.init_agents` for ai-service; `python -m app.agents.init_agents` for account-opening-worker) — what to do for LOCAL?

**Choice:** Option A+C — Mirror AKS initContainer as local-only docker-compose one-shot init services.

## Implementation Summary

### Services Added
- `ai-service-init`: Runs `python -m app.init_agents` for ai-service provisioning
- `account-opening-init`: Runs `python -m app.agents.init_agents` for account-opening-worker provisioning

Both init services:
- Use `depends_on: condition: service_completed_successfully`
- Gracefully skip when `FOUNDRY_PROJECT_ENDPOINT` is unset (exit 0)
- Soft-fail on provisioning errors (service comes up for devs without Azure AI access)

### Code Changes
1. **docker-compose.yml**: Added init service definitions with proper dependencies
2. **src/ai-service/app/services/anomaly_service.py**: Added AKS-safe guard for local Redis

   - Prevents locally-set `AZURE_CLIENT_ID` (needed for Foundry) from triggering Azure Managed Redis Entra/cluster auth against local redis container
   - Inert in AKS (Redis host is Managed Redis FQDN)
