### 1. Free-Text Planner Design (Complete — Awaiting Rulings)
**File:** `.squad/decisions/inbox/turk-free-text-planner-design.md`

**Summary:** Intent selection phase before `_required_evidence()` / `_plan_steps()`, only when `PlannerRequest.action_id` is absent. Reuses foundry plumbing (`model_call.py`, `extract_json`). New module `intent_model.py`. Server validates and decision-gates all model suggestions.

**Result shapes:** `kind` in {read, propose, refuse}. Read-only answers fed through new answer model. Actions follow existing evidence/propose path. Refusals are terminal with distinct failure codes.

**Reference resolution:** Deterministic `ReferenceResolver` between intent selection and evidence gathering. Model extracts hints only (name, account type, amount); resolver performs lookups and rejects ambiguity/no-match distinctly.

**Required backend support:** New read-only lookup endpoints for customer directory (pending Danny's ruling) and account listing by `userId`. Three tests per new endpoint (exact match, prefix, ambiguous/none).

**Payload validation:** Server constructs final payload; model drafts only. Validation: reference resolution → field merge → required field check → money scale normalization → action domain constraints → authority proposal. Unfillable payloads refuse, never clarify.

**Failure taxonomy:** Ten distinct codes — `planner_model_unavailable`, `intent_contract_invalid`, `objective_unmappable`, `forbidden_action`, `ambiguous_subject`, `subject_not_found`, `payload_unfillable`, `payload_invalid`, `evidence_unavailable`, `proposal_refused_by_authority`. No case completes as successful empty bundle.

**Open questions resolved by Danny:**
- Policy says credit adjustments are L2; refunds are L2 (confirmed)
- Action `requiredFields` not explicit; use action `hashFields` this pass or add explicit field to YAML
- Subject resolution requires new backend support (confirmed, add tools)
- Score override target value for vague objectives: model proposes, human signs (not clarify UX)

### 3. Facts Map Cross-Subject Bug (In Progress — Critical Priority)
**Status:** In-flight; blocking Linus

**Finding (Danny):** On multi-subject runs, `facts` map uses first-writer-wins merge. Evidence dict overwrite is last-writer-wins. Two collections disagree about subject on second lookup. Stale facts travel to authority attached to wrong customer's approval.

**Required fix:** One change addressing both evidence dict and facts map:
- Evidence dict: per-invocation keys within planner (bare, `#2`, `#3`...); authority-facing evidence keyed by tool id
- Facts map: carry only first-invocation tool results; no cross-subject merge

**Three tests:** Bundle shape, `already_gathered` refusal still fires, facts carry no cross-subject value after two-subject run.

**Wire bytes constraint:** Existing `propose` calls must remain byte-identical. Projection to tool-id set happens at authority seam only, not in citation layer or bundle structure.
